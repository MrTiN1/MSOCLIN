# Архитектура

Next.js App Router 16, React19, TypeScript, Tailwind4. Компоненты shadcn-style Button/Dialog основаны на Radix и CVA, Lucide, Motion с reduced-motion, React Hook Form + Zod. Интерфейс и сервер используют один расчёт стоимости; цены, варианты и правила дополнительных услуг берутся из PostgreSQL через Prisma6.

## Запись и расписание

Время хранится в `timestamptz` UTC. Расписание и UI интерпретируются в Europe/Moscow. TeamSchedule задаёт рабочие интервалы отдельно для каждой бригады по дню недели; отсутствие строки — выходной. ScheduleException блокирует произвольные интервалы. BookingResourceAllocation занимает [начало, начало+длительность+дорога). Перерыв блокирует пересекающие его записи. Слоты строятся из расписаний; статического массива времени нет.

Создание, отмена, перенос и изменения расписания используют одну транзакционную advisory-блокировку PostgreSQL. Это намеренная сериализация небольшого сервиса: упрощает согласованность между расписанием и заказами. Вторая независимая защита — частичный GiST EXCLUDE по teamId и `tstzrange`, WHERE active. Даже запись в обход приложения не может создать пересечение ресурсов. В параллельных запросах последняя доступная бригада достаётся одному клиенту, второй получает409. Две бригады могут занимать одинаковое время.

PENDING резервирует интервал до holdExpiresAt. Стандартная политика120минут, настраивается в CRM. Истёкшие резервы атомарно получают EXPIRED, allocations.active=false. Очистка выполняется перед чтением доступности, созданием/изменением заказа, открытием CRM и проверкой статуса. Отмена освобождает ресурс. CONFIRMED снимает TTL. Завершённые, отменённые и истёкшие заказы нельзя повторно активировать; нужна новая запись. Все переходы журналируются.

Повтор одного POST с тем же idempotencyKey не создаёт дубль; требуется тот же секретный клиентский accessToken. В БД хранится только SHA256 токена. Публичный status API раскрывает только номер, статус и время при правильном Bearer-токене; имени, телефона и адреса в ответе нет. Клиент проверяет свободные слоты заново перед выбором и отправкой; календарь обновляет даты каждые30сек, открытое окно времени — каждые15сек. Изменение длительности или времени на дорогу применяется к новым/перенесённым записям; существующие интервалы — сохранённый снимок условий.

## Калькулятор

ServicePrice содержит вариант, материал, стартовую сумму и единицу item/m2/quote. SiteSettings.pricing содержит минимальную сумму и правила по slug услуги. Процентные опции считаются от базы, фиксированные — один раз на заказ. Минимум применяется после допуслуг один раз. Все оценки предварительные. quote-услуги не притворяются точным расчётом: объём требует консультации. Менеджер может зафиксировать согласованную сумму в заказе; выручка учитывает только COMPLETED.

## Авторизация и защита

Без публичной регистрации. Пароли scrypt с уникальной солью; подписанная8-часовая сессия jose HS256 в HttpOnly, SameSite=Strict cookie, Secure в production. Каждый административный API повторно проверяет пользователя и sessionVersion в БД. Выход отзывает все сессии пользователя. Origin проверяется на всех изменяющих формах; APP_URL обязателен в production. RateLimit хранится в БД, работает между процессами. TRUST_PROXY включается только за доверенным прокси; на Vercel входящий x-forwarded-for должен перезаписываться платформой. Нет секретов в NEXT_PUBLIC_*.

Административные операции валидируются allowlist-схемами Zod; клиент не может изменить произвольные модели/поля. Записи аудита не публикуются. В заголовках DENY iframe, nosniff, restricted base/object/form и referrer policy. Ввод отображается как React-текст, без raw HTML. Для производственной эксплуатации нужны HTTPS и настроенный домен.

Фото загружаются только администратором в Vercel Blob. Разрешены JPEG/PNG/WebP до5МБ; Sharp проверяет реальные данные и лимит пикселей, перекодирует WebP, убирает EXIF/метаданные, ограничивает2000px. SVG и произвольные файлы не принимаются. Имена случайные. Галерея публикует только rightsConfirmed=true; отзывы — только verified=true и с URL источника.

## Telegram и outbox

NotificationLog создаётся в транзакции с заказом. После ответа отправляется уведомление только в TELEGRAM_CHAT_ID. При отсутствии настроек статус UNCONFIGURED, заказ остаётся сохранённым. Ошибки — RETRY без токенов и персональных данных в логах. Повторная доставка — защищённый cron endpoint или CLI. Забранный отправителем outbox имеет SENDING; зависшие более10минут могут повторяться. Доставка at-least-once: при сбое между Telegram API и обновлением БД возможен повтор уведомления; запись заказа не дублируется.

Webhook требует секретный заголовок Telegram, совпадение chat.id и пользователя из TELEGRAM_ADMIN_IDS. Кнопки подтверждения/отмены вызывают ту же транзакционную бизнес-логику, что CRM. Повтор на уже обработанном заказе не меняет статус незаконно. «Открыть заказ» ведёт в защищённую CRM. Внешняя доставка без реального токена не тестировалась.

## Границы

Не реализована онлайн-оплата — она не запрошена. Не выдуманы отзывы, партнёры или результаты работ. CRM и сервер галереи готовы, но правомерные фотографии и проверенные тексты отзывов должен предоставить владелец. Юридические реквизиты и окончательная политика хранения должны быть утверждены перед запуском. Учёт маршрутов — настраиваемый фиксированный запас на дорогу, без геокодинга. Администратор управляет бригадами и графиком; отдельные кабинеты мастеров не запрошены.
